# 开局 NEXT：重做决策与技术说明

日期：2026-10-12。此文描述 v0.3 当前代码，不把旧方向的能力算入新版。

## 用户反馈决定问题定义

用户明确指出原“衡局”游戏经济工具难以理解、缺少玩家价值，要求全部重来，参考王者营地和微信“天元之弈助手”，同时做出自己的东西。因此本轮从玩家熟悉的英雄资料站入手，核心问题为：

> 我会玩的英雄有限。面对这一局的阵容，我应该考虑谁、接受什么代价，下一局具体练什么？

这适合做一个个人备战台。该场景的真实需求和差异价值还需实际访谈和试用确认，不能因界面完成就宣布创新已验证。

## 研究依据及边界

1. 用户确认“天元之弈助手”位于微信公众号/小程序，没有网址。未获得其内部页面，本轮没有声称已完整体验或逐项比较。
2. 读取腾讯王者营地公开推广页 https://pvp.qq.com/cp/a20181201camp/index.htm ，了解其公开介绍的战绩工具、资讯攻略视频、社区和赛事方向。该页面较旧，不能代表当前产品功能全貌。
3. 获取 https://pvp.qq.com/web201605/js/herolist.json ，目录为 133 位英雄。分路来自 roles 字段，职业来自 hero_type / hero_type2，两者分开映射。
4. 读取官方 herodetail/{id}.shtml 技能页，按 GB18030 解码，解析技能名称与说明。117 位解析成功，16 页返回 404；失败清单及目录 SHA-256 随快照保存。
5. 不使用没有依据的实时胜率、对位克制率、账号战绩、装备强度或版本标签。

## 用户流程

英雄查询与个人熟练度 → 选择双方阵容 → 查看候选及能力变化 → 保存 / 导出备战卡 → 手动记下比赛转折 → 首页提醒下一局目标。

这条连续流程是当前设计重点。它是待验证的产品差异，不是宣称行业首创。没有制作社区、赛事直播等规模很大但与这一问题无关的模块。

## 架构

浏览器使用 React、TypeScript 和 Vite。前后端复用输入 schema 与推荐规则；Zod 在服务端校验输入，Node HTTP 提供接口，Node SQLite 保存本机资料。模型密钥只保存在服务端。

英雄与技能使用固定 JSON 快照。40 位英雄的战术标签、取舍和练习笔记由项目整理，不来自实测对局统计。推荐在本机计算，服务端保存卡片前再次计算，以防提交已失效的候选。

数据层分开保存英雄池、阵容、备战卡和手记。手记改写 nextAction 时，完成状态重置。卡片打开时恢复保存时选择，但根据当前英雄池重算推荐。浏览器本地阵容草稿优先恢复；点击“保存阵容”再写入 SQLite。

## 推荐如何产生

候选须符合官方目录的分路，且拥有本项目战术笔记；排除其他我方位置、全部敌方位置和禁用英雄。勾选“只从我的英雄池里选”时进一步限制。

排序使用明确但尚未校准的启发式：
- 能补充已标注阵容缺失的前排、先手、法术或物理输出，每项加 4。
- 本命加 7，熟练加 5，正在练加 1，未声明熟练度不加分。
- 已标注的对手存在机动切入，候选有保护能力时加 3。
- 同分按英雄 ID 稳定排序，最多显示 3 位。ID 次序没有竞技含义。

界面不展示这个分数为胜率。理由、代价与能力变化直接对应已知标签。缺少笔记的队友或对手会产生范围提示。空位置保留未知；“—”是已标注英雄暂未覆盖，不代表整个队伍绝对没有这种能力。选择比较时移除“我的位置”的原英雄，再计算候选加入后的差异。

## 可选 AI 解读

接口使用兼容 chat/completions 的服务，输入为所选英雄官方技能、双方英雄名称和已有规则摘要。系统约束禁止编造胜率、账号战绩、版本强度或保证胜利。返回必须满足“一句建议 + 三步行动 + 局限”的结构。

结构校验不证明战术内容正确。当前仅模拟服务验证协议；未配置真实服务、未消耗付费模型额度、未做真实生成质量评测。阵容或候选变化时前端使已有及未完成解读失效。响应超时、格式错误或服务失败均给出失败反馈，可再次请求。

## 工程边界

本地单用户服务，仅允许本机 Host 并校验写入 Origin；输入 128 KB 上限；模型请求 25 秒超时且单请求执行；英雄 ID、重复阵容和日期等由服务端校验。这些措施经过所列测试，但不构成全面安全审计。公网部署、多账号、权限管理及备份恢复界面未实现。

官方图片远程加载，离线或请求失败时回退到姓名标识。没有用本地下载绕过远端资源条件。技能快照可离线读，但可能落后于游戏实际更新。

## 下一阶段可检验的质量门槛

- 至少邀请 5 位真实玩家，不提示答案地完成查英雄、建池、选人、复盘流程，记录任务完成情况及困惑。
- 用玩家真实常用英雄检查 40 位笔记覆盖率，扩充前逐条核对官方机制，邀请熟悉对应位置的玩家复核。
- 构建固定阵容集，对比“仅熟练度”“仅阵容标签”“组合建议”，由盲评判断理由是否有用。不得用自己生成的标签一致性当成实战有效性。
- 接通用户选定的真实模型后评估建议的机制错误、来源一致性、延迟和成本；先评测再宣传 AI 质量。
- 核实赛事实际赛项、报名及日期，整理原始过程证据，制作正式视频和 PDF。

这些是未完成的验收门槛，不在本轮通过项中。
