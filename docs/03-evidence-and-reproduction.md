# 开发证据与复现方案

## 从现在保留什么

每个实际迭代记录：用户真实需求或已授权范围 → AI 建议与响应 → 修改文件 → 执行命令和输出 → 失败与修复 → 验收结论 → Git 提交。一次提交对应实际完成的逻辑单元；不在开发结束后拆分代码伪装连续过程，不改写时间戳。

Git 提交目前由 `Codex (AI assistant) <codex-ai@example.invalid>` 标识自动产出。此身份不等同于参赛者自己的 GitHub 账号，也不假称用户手写代码。之后关联远程仓库时保持原有历史。

`evidence/iterations/` 保存便于索引的工作记录。原始聊天导出、截图和录屏另行保存，索引中指向相应原件。若含密钥或个人信息，公开版本须明确标记脱敏；不要将原始私密材料提交到公开仓库。

## 三条拟重点留存的核心链

1. **意图与结构化输入链**：从真实任务提出约束与提取要求，观察误解或缺字段，用户指出问题，AI 调整契约与校验，复测。
2. **核心算法与解释链**：用户给出预期行为，AI 实现搜索、检查或求解，对漏报/误报提供真实反馈，修复并保留前后证据。
3. **变更与完整交互链**：用户提出修改，验证影响范围、历史记录或重放结果，发现并修复真实问题。

这三条是记录目标，不是已经发生的事实。遇到其他真实问题也可以成为有效迭代；不故意制造 Bug 或脚本化伪造互动。

## 两个层次的可复现性

**软件与行为复现**：Git 历史、依赖锁文件、环境说明、结构化数据样例、数据库初始化和固定规则测试，支持恢复每个阶段的代码及确定性行为。

**AI 演进审计**：保存实际使用的工具/模型名称与可获取版本、时间、完整提示、上下文、实际回复、接受的修改及对应代码差异。模型服务存在随机性和版本变化，相同 Prompt 不承诺重新生成字节相同的代码；temperature=0 也不是此类保证。

已经保存的响应和补丁可以重放历史产物，但应称为“保存的产物重放”，不能称为“实时模型再次生成了完全相同代码”。

## 十分钟启动的验收方法

- 第一版可运行后提供准确 Node.js 版本范围、锁文件、环境变量模板、单一启动入口和重置样例方法。
- 演示路径无需模型账号，界面明确标注预置或合成数据；真实 API 路径给出独立配置和测试步骤。
- 从干净目录按 README 操作，记录机器、系统、网络条件、下载/安装时间与首次可操作时间；失败同样保存。
- 若预装 Node.js、提前下载依赖或使用缓存，必须写明计时前提；不把本机热启动时间当成首次复现时间。
- 原文没有说明离线演示能否替代真实 AI 复现；最终材料必须同时讲清两者，并以官方确认和实测为准。

## 演示视频规划：约 6 分 30 秒

| 时间段 | 内容 |
| --- | --- |
| 0:00–0:40 | 一个具体真实痛点，说明目标用户与当前做法 |
| 0:40–2:50 | 最终选题的输入、核心结果、解释、用户操作与导出闭环 |
| 2:50–5:10 | 至少 2 分 20 秒真实 AI 协同过程：提示、出错、用户引导、代码修改、验证与提交 |
| 5:10–6:00 | 有来源的试用与对照结果，说明样本局限 |
| 6:00–6:30 | 干净环境复现入口、架构核心与使用方式 |

AI 协作段必须来自实际记录。说明哪些片段经过剪辑/加速，不把剪辑时长用作真实开发速度证据。最终检查视频编码、分辨率、总时长和过程展示时长。

## 技术 PDF 规划：建议 16–22 页

覆盖问题与用户、原始场景、产品闭环、意图契约、架构、核心算法、结果解释、三条迭代案例、复现方法、实验结果、已知局限与依赖声明。具体章节在选题确定后调整。不超过 30 页；最终必须渲染检查可读性、换页、图表和链接。
